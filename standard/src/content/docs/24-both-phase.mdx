# 24. Both-phase API [#lua.both]
> **Normative.** This chapter defines the Cook Lua API surfaces that are available in both register-phase and execute-phase Lua. The behavioural contract — signatures, error model, working-directory rooting — is identical across phases; only the surrounding scheduling differs.

## 24.1. `cook.sh` [#lua.cook-sh]
**Signature.** `cook.sh(cmd: string) -> string`
**Phase.** Both.

`cook.sh` executes `cmd` via `/bin/sh -c` in the Cookfile's working directory with the inherited environment and nothing merged onto it — a declared variable is not a process-environment entry (§{decl.config}), so `$NAME` in the command names an ambient variable, never a build variable — and returns the captured standard output as a string. A non-zero exit status MUST be reported as a Lua runtime error. The function name is intentionally shared between phases because the user-visible behaviour — "run this command and give me its stdout, error on non-zero" — is the same in both; only the surrounding scheduling differs.

In the **register phase**, `cook.sh` is a utility for control-flow decisions during registration (feature detection, tool discovery, reading version files). It is NOT the mechanism by which work units are recorded; use `cook.add_unit` for that. The capture-mode contract of §{exec.capture} applies: a register-phase `cook.sh` call MUST be deterministic with respect to the Cookfile source and the register-phase record accumulated so far, and MUST NOT modify files under the working directory in a way that affects declared outputs.

In the **execute phase**, `cook.sh` runs on the worker VM that is evaluating an execute-phase Lua chunk — for example, a `cook` / `test` / `probe` step's `>{ … }` body payload (§{lua.using-block-globals}), whose Lua runs in that step's own execute-phase work unit. As of CS-0134 a recipe body carries no imperative region, so there is no coalesced "body unit"; the former imperative-region run no longer exists for recipes (§{exec.body-bundling} is vacuous for recipe bodies). `cook.sh` remains the mechanism by which a `lua_line` or `lua_block` shells out, and inside a `chore` body it is the call into which the chore's shell steps desugar under the single-drain model of §{chores}.

**Both streams are captured, and both are attributed (CS-0188).** Stdout is captured and returned to the calling Lua code, and stderr is captured too. A conforming implementation MUST attribute both to the calling **unit**, and MUST reach the user's diagnostic channel with each carrying its stream of origin, so that a warning printed by one unit's command is not confused with another's. A unit whose body calls `cook.sh` more than once MUST preserve the order of those calls in what it reports; within a single call the two streams are buffered separately, and their relative interleaving is not preserved and MUST NOT be presented as though it were.

Until CS-0188 this section said only that "stderr is streamed to the worker's stderr", which named a destination rather than an owner and was not implemented: the reference implementation discarded a successful `cook.sh` call's stderr entirely, so a command that compiled with warnings reported none of them. Attribution is stated here rather than left to the diagnostic layer because the worker's stderr is one file descriptor shared by every unit running in parallel, and bytes written to it carry nothing that says which unit produced them.

## 24.2. `cook.load_module` [#lua.cook-load-module]
**Signature.** `cook.load_module(name: string) -> table`
**Phase.** Both.

`cook.load_module` resolves `name` against the calling work unit's source Cookfile and returns the module's Lua table. The lookup is **lexical per Cookfile** (§{mods.use-scope}): an imported Cookfile's body unit, whose `working_dir` is its own import directory, resolves `cook.load_module("foo")` against `<import_dir>/cook_modules/foo.lua`. The importing Cookfile cannot reach into the imported Cookfile's `cook_modules/` and vice versa.

A conforming implementation MUST configure `package.path` and `package.cpath` for the calling Lua VM such that sub-requires within a multi-file module resolve against the project's `cook_modules/` search paths rather than the host system's Lua paths. A conforming implementation MUST allow C extension modules (`.so`/`.dll`) to be loaded during `cook.load_module` evaluation. [amended CS-0066]

When `cook.load_module` is exposed on the execute-phase Lua VM, the execute-phase implementation MUST honour the same four-path resolution order used at register phase. Recipe-body Lua scripts that call `cook.load_module(name)` directly therefore see the same set of candidate paths as register-phase callers, eliminating "works at register but not at execute" surprises. [amended CS-0069] In the reference implementation both phases probe the ONE candidate list and compose `package.path`/`package.cpath` through the ONE composer in `cook_contracts::layout` (COOK-393), so the agreement is structural rather than manually mirrored (informative).

A conforming implementation MUST report a runtime error when `name` does not resolve to a file under the calling Cookfile's `cook_modules/`. The diagnostic MUST identify `name` and the absolute path(s) that were searched.

The body of a module loaded into the execute-phase VM MUST NOT call register-only API (`cook.add_unit`, `cook.exec`, `cook.interactive`, `cook.step_group`, `cook.recipe`). A conforming implementation MUST surface such a call as the §{rationale.execute-phase-api} runtime error. Module functions whose bodies are restricted to both-phase API (`cook.sh`, `var`, `cook.probes`, `cook.platform`, `fs.*`, `path.*`) work in either phase; module authors document per-function which phase a function targets.

`cook.load_module` is the resolver behind the `use` declaration (§{mods.use}). The codegen for `use foo` emits `local foo = cook.load_module("foo")` at the top of the Cookfile's register-phase Lua, and prepends the same binding to every execute-phase body unit's `lua_code` payload, so the alias `foo` is in scope for both phases of every recipe in the declaring Cookfile.

Module lifecycle — the top-level chunk's once-per-VM execution, the `init()` call, per-VM caching, cross-VM rehydration, and cycle detection — is specified in §{mods.lifecycle}, not here. This section defines only the call surface.

## 24.3. `var` [#lua.var]
**Type.** `table` (read-only outside a `config_body`)
**Phase.** Both.

`var` is the declared-variable namespace of §{decl.config}: a global table whose contents are exactly the names the Cookfile's `config` blocks exported. It is NOT the process environment, and a conforming implementation MUST NOT seed it from one (CS-0172). The table it exposes has three semantic distinctions from a bare table:

- **Reads are checked.** `var.NAME` for a name no config block exported MUST raise a Lua runtime error suggesting the closest exported names. Presence-guarding an undeclared variable (`if var.maybe then`) is therefore not a supported idiom — declare it with a default instead.
- **Writes are refused.** An assignment through `var` outside a `config_body` MUST raise. A declared value is a determinant of every unit keyed against it (§{exec.cache.abstract}); mutating it mid-pass would invalidate a key already computed.
- **Values carry their declared type** on the register-phase VM: `string`, `number`, or `boolean` per §{decl.config}.

On the **execute-phase** VM, values are visible in their **string form** (§{decl.config}). A conforming implementation MUST reject, at register phase, a Lua-body unit (§{steps.lua}) whose statically-recorded reads (§{exec.cache.lua-variable-reads}) name a variable whose declared value is not a string — naming the variable and the phase. Silently handing the body a truthy `"false"` is the failure this rule exists to prevent; the author either interpolates `$<NAME>` or branches in a `register` block.

Within a `config_body` (§{decl.config}), `var` is the writable output sink instead — see §{lua.var-sink}.

### Example 24.3.1

```cook
config
    var.compiler = "clang"
    var.optimize = "-O2"
    var.symbols  = true

cc.toolchain({
    compiler      = var.compiler,
    extra_cflags  = var.optimize,
    debug_symbols = var.symbols,
})
```

The config body writes the sink; the top-level module call reads the same names through the read-only global, with `var.symbols` arriving as a boolean. The names are equally resolvable as `$<compiler>` / `$<optimize>` / `$<symbols>` placeholders in recipe bodies (§{phl.cook-step}), where `$<symbols>` interpolates the string `true`.

## 24.4. `cook.probes` [#lua.cook-probes]
**Phase.** Both. [Pinned by CS-0070.]

`cook.probes` is the Cook-managed key/value store available to register-phase and execute-phase Lua. Its purpose is to let modules persist register-phase computations (compiler detection, package finder results) into a form that execute-phase code can read without redoing the work.

### 24.4.1. `cook.probes.get` [#lua.cook-probes-get]
**Signature.** `cook.probes.get(key: string) -> any`

On the execute-phase VM, `cook.probes.get(key)` MUST read from the per-run probe-value store specified in §{cat.probes.exec}. The store is populated by completed probe units in topological order before any consuming unit dispatches. An unknown key returns `nil`. `cook.probes.set` is NOT available on the execute-phase VM (deprecated entirely per CS-0074).

On the register-phase VM, `cook.probes.get(key)` returns the value previously stored under `key` via `cook.probes.set` (or `nil` if no value is stored). The value MUST round-trip through any serialisation the implementation uses for persistence; non-serialisable values (Lua functions, userdata, coroutines) MUST raise a Lua runtime error when passed to `cook.probes.set`.

### 24.4.2. `cook.probes.set` [#lua.cook-probes-set]
**Signature.** `cook.probes.set(key: string, value: any) -> nil`

> **Deprecated** (CS-0074, v0.11; renamed `cook.cache` → `cook.probes` in CS-0136). Not available on the execute-phase VM; full removal deferred to a later 1.x revision. Use `cook.probe` (§{cat.probes}) for memoised values.

Stores `value` under `key`. Subsequent `cook.probes.get(key)` returns `value` (or its deserialisation-equal counterpart).

A register-phase write MUST be persisted by the implementation in a way that survives across Cook invocations: a register-phase `set` followed by a later register-phase `get` in a different Cook invocation MUST return the previously-stored value. The on-disk format is implementation-defined.

`cook.probes.set` is NOT available on the execute-phase VM; a conforming implementation MUST raise a Lua runtime error when `cook.probes.set` is called from execute-phase Lua.

### 24.4.3. `cook.probes.scope` [#lua.cook-probes-scope]
**Signature.** `cook.probes.scope(label: string) -> table`

> **Deprecated** (CS-0074, v0.11; renamed `cook.cache` → `cook.probes` in CS-0136). Not available on the execute-phase VM; full removal deferred to a later 1.x revision. Use `cook.probe` (§{cat.probes}) for memoised values.

Returns a "scoped" table view whose `get(key)` and `set(key, value)` operations are equivalent to `cook.probes.get(label .. ":" .. key)` and `cook.probes.set(label .. ":" .. key, value)` respectively. The label string MUST NOT contain the `:` character; a conforming implementation MUST raise a Lua runtime error on such a label.

Scopes are conventionally named after the module that owns them (e.g. `cook_cc:toolchain`, `cook_cc:find:raylib`) to prevent key collisions between modules.

## 24.5. `cook.export` and `cook.import` [#lua.cook-exports-imports]
**Phase.** Register only. [CS-0200; was "Both" and cited CS-0071, see below.]

This section is retained in the both-phase chapter for stable anchors; the surface is register-phase and calling either function from an execute-phase VM MUST raise, in the manner of §{lua.cook-probes-set}.

`cook.export` and `cook.import` are the Cook-managed transitive-link-info channel used by target makers (e.g. `cc.bin`/`cc.lib` per §{cat.cc.transitive}) to publish a target's outward-facing fields and by consumers to read them.

### 24.5.1. `cook.export` [#lua.cook-exports]
**Signature.** `cook.export(name: string, info: table) -> nil`

Records that the target named `name` exposes the fields in `info`. The `info` table's shape is conventionally established by the publisher's module documentation; for `cc` targets the conventional shape is documented in §{cat.cc.transitive}. Beyond requiring a Lua table, the Standard constrains `info` only to be **serialisable under the §{cat.probes.values} value contract** (CS-0198): the exported value crosses VM boundaries as JSON, so a table that JSON cannot faithfully carry — mixed string/integer keys, an array with holes, a non-finite number, a non-UTF-8 string, a function/userdata/cycle anywhere within — MUST be rejected with a register-phase (or execute-phase, per the calling VM) Lua error naming the offending path, in the manner of §{cat.probes.values}. A conforming implementation MUST NOT silently drop or coerce the unserialisable parts: before CS-0198 the reference implementation did exactly that (mixed keys dropped, holes compacted, NaN to `null`, non-UTF-8 lossy-substituted), so an export could differ from what the author published with no diagnostic.

A conforming implementation MUST persist the exported value in a way that subsequent register-phase `cook.import(name)` calls, within the same Cookfile evaluation, return the exported value.

### 24.5.2. `cook.import` [#lua.cook-imports]
**Signature.** `cook.import(name: string) -> table?`

Returns the table previously published for `name` via `cook.export`, or `nil` if no export has occurred.

A conforming implementation MUST resolve `cook.import` against the **same workspace's** export records — `cook.import` MUST NOT cross workspace boundaries. The interaction with cross-Cookfile composition is: a target maker invoked from an imported Cookfile (§{comp.import}) publishes exports against the workspace-global table, but resolution by recipe name in a different Cookfile uses the qualified name `alias.name` per §{comp.qualified-refs}.

### 24.5.3. Why this is register-phase only [#lua.cook-exports-phase]

The paragraph this replaces permitted "a per-worker scratch store when the recipe body is both producer and consumer", setting the minimum bar at round-tripping "within a single worker VM". §{mods.lifecycle.rehydration} simultaneously required a register-time export to be observable to an execute-phase `cook.import`. A per-worker store cannot satisfy that, so the two clauses could not both be met, and the reference implementation met the permissive one: its execute-phase VM built an empty per-VM table, never seeded it, and returned `nil` for every register-time export.

Neither clause described anything a module needed. The transitive-link walk that motivates the whole channel (§{cat.cc.transitive}) runs at register time, because its product is the compile and link command lines, which must exist before any unit is captured. Reading an export also forces the referent's recipe body (§{reg.require-recipe}), which is a register-phase act by definition.

The per-worker store was additionally unsound on its own terms: units of one recipe are dispatched from a shared queue to whichever worker is free, so "within a single worker VM" is not a scope an author can rely on. Two units of one recipe routinely land on different VMs, making an execute-phase export visible or invisible according to scheduling.

CS-0200 therefore withdraws the execute-phase half rather than implementing it, matching the treatment §{lua.cook-probes-set} gives `cook.probes.set` for the same reason: a write into a per-VM store that no other unit can observe is refused by name rather than allowed to half-work.

## 24.6. `cook.platform` [#lua.cook-platform]
**Type.** `table`
**Phase.** Both.

`cook.platform` is a Cook-managed read-only table exposing the host platform's identity. The following fields MUST be populated by a conforming implementation:

| Field | Type | Value |
|---|---|---|
| `os` | string | `"linux"`, `"darwin"`, `"windows"`, or `"unknown"`. |
| `arch` | string | `"x86_64"`, `"aarch64"`, `"arm"`, `"riscv64"`, or `"unknown"`. |
| `triple` | string | The host's compiler target triple, e.g. `"x86_64-unknown-linux-gnu"`, `"aarch64-apple-darwin"`. Implementation-defined when the host is not recognised by the implementation's target-triple resolver. |

The values MUST be identical between the register-phase Lua VM and every execute-phase worker VM within a single Cook invocation. Implementations realise this by sharing a single source-of-truth resolver across VMs; the reference implementation does so via `cook-lua-stdlib::platform`.


**Forcing (register phase, inside a recipe body).** When `cook.import(N)` is called from within a recipe body during the register phase and `N` has published no export yet, a conforming implementation MUST force `N`'s body to completion before returning, to the standard §{lua.cook-require-recipe} defines — same transitivity, same at-most-once rule, same prohibition on degrading the forcing to a silent skip. The call then returns `N`'s export.

Forcing is a property of **reading** an export, not of declaring a dependency. A module resolving a link reference calls `cook.import` at exactly the moment it needs the referent's body to have run; requiring it to arrange that separately, through an API whose other effect is a whole-recipe ordering edge, is what coupled export resolution to execution ordering in the first place (§{lua.cook-dep-order}, CS-0161).

Three boundaries on the rule. Where `N` has already exported, the implementation MUST NOT force — the value is returned directly, so the common case stays a lookup and the rule is a no-op once a body has run. Where the call is made **outside** a recipe body — a `cook.on_register_complete` finalizer (§{lua.cook-on-register-complete}) reading exports to emit a compilation database, say — the recipe set is closed and forcing is illegal; `cook.import` MUST remain a plain lookup there, returning `nil` for an absent export. And where `N` has no export and is not a recipe registered in the current pass, the implementation MUST surface the forcing error rather than returning `nil`: a silent `nil` is the mislink §{lua.cook-require-recipe} exists to prevent, and a caller that merges the result into a link line emits one missing the library.
### Example 24.6.1

```lua
if cook.platform.os == "darwin" then
    cook.add_unit({
        command = "install_name_tool -id @rpath/libfoo.dylib build/lib/libfoo.dylib",
        cache   = false,
    })
end
```

The `cook.platform.os` check happens at register time on the register-phase VM; the unit is recorded only on macOS hosts.

## 24.7. `cook.dep_output` and `cook.dep_output_list` [#lua.cook-dep-output]
**Phase.** Both.

`cook.dep_output` and `cook.dep_output_list` are the Lua-side counterpart of the `$<NAME>` string-substitution surface (§{xref.string-substitution}). A `>{ … }` or `test >{ … }` body that needs to reference another recipe's output uses these functions instead of textual placeholder substitution.

### 24.7.1. `cook.dep_output` [#lua.cook-dep-output-single]
**Signature.** `cook.dep_output(name: string) -> string`

Returns the named recipe's output list joined by single space characters. Equivalent to the textual expansion of `$<NAME>` per §{xref.string-substitution}.

If the named recipe's output list is empty, returns the empty string; a conforming implementation MUST emit a warning at register time naming the referring recipe and the referent. The reference itself is not an error.

If `name` does not name a recipe in scope, a conforming implementation MUST raise a Lua runtime error at the calling step's register time.

### 24.7.2. `cook.dep_output_list` [#lua.cook-dep-output-list]
**Signature.** `cook.dep_output_list(name: string) -> table`

Returns the named recipe's output list as a 1-indexed Lua table of strings. Equivalent to `cook.dep_output(name)` but preserved as a sequence so that callers can iterate, index, or apply path accessors (§{xref.path-accessors}) per-element.

Same error model as `cook.dep_output`.

### Example 24.7.1

```cook
recipe libs
    cook "build/lib/libfoo.a" { ar rcs $<out> ... }
    cook "build/lib/libbar.a" { ar rcs $<out> ... }

recipe app
    cook "build/bin/app" >{
        local libs = cook.dep_output_list("libs")
        local cmd = "gcc -o " .. output .. " main.c"
        for _, lib in ipairs(libs) do
            cmd = cmd .. " " .. lib
        end
        cook.sh(cmd)
    }
```

The `cook.dep_output_list("libs")` call returns `{ "build/lib/libfoo.a", "build/lib/libbar.a" }`. An equivalent shell-body recipe would use `$<libs>` per §{xref.string-substitution}.

## 24.8. `cook.json_decode` and `cook.yaml_decode` [#lua.cook-codecs]
**Phase.** Both.

### 24.8.1. `cook.json_decode` [#lua.cook-json-decode]
**Signature.** `cook.json_decode(text: string) -> table | string | number | boolean | nil`

Parses `text` as JSON and returns the corresponding Lua value: objects and arrays become tables (arrays 1-indexed), strings/numbers/booleans map to their Lua counterparts, and JSON `null` becomes `nil` (as an object member value, the key is absent). Malformed JSON is a Lua runtime error tagged `json error`.

### 24.8.2. `cook.yaml_decode` [#lua.cook-yaml-decode]
**Signature.** `cook.yaml_decode(text: string) -> table | string | number | boolean | nil`

Parses `text` as YAML under the same value mapping as `cook.json_decode`. Malformed YAML is a Lua runtime error tagged `yaml error`.

### Note 24.8.1

The codecs are pure functions of their argument; they perform no I/O and consult no phase state. A conforming implementation MUST install both on the register-phase VM and on every execute-phase worker VM, so a probe `produce` body (§{cat.probes.api}) behaves identically whether it is evaluated by the `ingredients <probe>` register pre-pass or by a demand-driven worker (CS-0123).

## 24.9. `cook.tools.id` [#lua.cook-tools-id]
**Phase.** Both.

**Signature.** `cook.tools.id(name: string) -> { hash: string, path: string } | nil`

Resolves `name` on the current PATH and returns its **canonical tool identity**: `hash` is the lowercase-hex SHA-256 of the resolved binary's content — a machine-independent identity — and `path` is the location it resolved to right now. Returns `nil` when the name does not resolve. The call MUST resolve and hash the binary as it exists at call time; an implementation MAY memoize the hash per resolved path within a single run.

The function exists so a module can fold a **real toolchain identity** into a probe value it seals (§{mods.authoring.seal}) without hashing large binaries in Lua: the `hash` field is the value to fold — a compiler upgrade changes the bytes, the hash, the sealed value, and therefore every sealing unit's key. The `path` field is location metadata for invocation and MUST NOT be folded into a sealed value: a machine-specific path in a sealed value re-keys identical toolchains across machines, defeating the cross-machine reuse §{exec.cache} exists to provide (the same rule the native `tools` producer's value shape enforces, §{cat.probes.decl}).

### Note 24.9.1

A conforming implementation MUST install `cook.tools.id` on the register-phase VM and on every execute-phase worker VM, so a probe `produce` body behaves identically on the register pre-pass and the demand-driven worker path (the CS-0123 rule, applied to this API). The reference implementation backs both installs with the same per-run tool-hash memo the probe-fingerprint machinery uses, so calling `cook.tools.id` never re-hashes a binary the fingerprint pass already read. (CS-0158.)
