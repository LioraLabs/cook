## Cold, then cached, then one edit

The first run cooks all five nodes. The second run touches nothing: every key is already in the store. Then one chapter changes, and exactly the nodes downstream of it rebuild. The count for the other chapters, untouched, stays cached.

> [!tip] Why `one.count` stayed cached
> Each fan-out unit is keyed on its own input. Editing `two.txt` changes one key. The total depends on all three counts, so it rebuilds; so does the report, which depends on the total. That is the whole model: [[9. Caching and cache trust|the key is built from what you declared]], and nothing else.

## See the key for yourself

`cook why` prints every determinant behind a unit's key, with its hit or miss status. Ask it about the total:

```sh
cook why report/build/total.txt
```

Read [[9. Caching and cache trust]] for `seal`, the shared store, and `cook cache verify`.
